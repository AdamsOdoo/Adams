## 1. Sales order lifecycle

Source: https://raw.githubusercontent.com/odoo/odoo/19.0/addons/sale/models/sale_order.py — Accessible, 2026-07-16.

- [Fact] `sale.order.state`: `('draft', "Quotation")`, `('sent', "Quotation Sent")`, `('sale', "Sales Order")`, `('cancel', "Cancelled")` [quote]. **No "done" state in 19** — locking is a separate boolean: `locked = fields.Boolean(help="Locked orders cannot be modified.", default=False, copy=False, tracking=True)` [quote].
- [Fact] `action_confirm()`: validates `_confirmation_error_message()`, writes `state='sale'` + `date_order` (`_prepare_confirmation_values()`), calls `_action_confirm()` extension hook, then auto-locks via `_should_be_locked()` gated on group `sales_team.group_auto_done_setting`; optional confirmation email with context `send_email`.
- [Fact] Delivery creation: `sale_stock`'s `sale.order.line._action_launch_stock_rule` fires on line create when order state `sale` and on write of `product_uom_qty`; skips lines where `line.state != 'sale' or line.order_id.locked or line.product_id.type != 'consu'`; runs `stock.rule` procurements ("procurement will launch `_run_pull`, `_run_buy` or `_run_manufacture`" [quote]) then `pickings_to_confirm.action_confirm()`. Source: https://raw.githubusercontent.com/odoo/odoo/19.0/addons/sale_stock/models/sale_order_line.py — Accessible, 2026-07-16.
- [Fact] Cancellation: base `action_cancel` refuses locked orders ("You cannot cancel a locked order. Please unlock it first." [quote]), cancels **draft** invoices only, sets `state='cancel'`. `sale_stock` override cancels all non-done pickings: `self.picking_ids.filtered(lambda p: p.state != 'done').with_context(skip_cancel_activity=True).action_cancel()` [quote] — **done pickings are preserved**. `delivery_status` computed field: pending/started/partial/full. Source: https://raw.githubusercontent.com/odoo/odoo/19.0/addons/sale_stock/models/sale_order.py — Accessible, 2026-07-16.
- [Fact] Invoicing policies (user docs): "Invoice what is ordered" (default — invoice once confirmed) vs "Invoice what is delivered" (invoice as quantities are delivered; delivery validation required). Changing the global default affects only newly created products. Source: https://www.odoo.com/documentation/19.0/applications/sales/sales/invoicing/invoicing_policy.html — Accessible, 2026-07-16.
- [Fact] `invoice_status`: `no` / `to invoice` / `invoiced` / `upselling`; orders not in `sale` → `no`.
- [Open question] `sale.order.cancel` confirmation-wizard trigger conditions in 19.0 unverified. [Open question] Official 19.0 user-doc page for "Lock Confirmed Sales" not located (source-verified only).

## 2. Delivery / stock workflow

Source: https://raw.githubusercontent.com/odoo/odoo/19.0/addons/stock/models/stock_picking.py — Accessible, 2026-07-16 (note: `StockPickingType` lives in this file; a separate `stock_picking_type.py` 404s).

- [Fact] `stock.picking.state` [quote of selection]: `draft`, `waiting` (Waiting Another Operation), `confirmed` (Waiting), `assigned` (Ready), `done`, `cancel`. Help: draft — "The transfer is not confirmed yet. Reservation doesn't apply"; assigned — at least one / all products reserved (depending on move type).
- [Fact] Reservation methods on `stock.picking.type`: `reservation_method` = `at_confirm` / `manual` / `by_date` ("How products in transfers of this operation type should be reserved." [quote]) + `reservation_days_before`(_priority). User docs: Inventory → Configuration → Operations Types. Source: https://www.odoo.com/documentation/19.0/applications/inventory_and_mrp/inventory/shipping_receiving/reservation_methods.html — Accessible, 2026-07-16.
- [Fact] `action_assign` confirms drafts, sorts moves by priority/deadline/date, calls `moves._action_assign()`; reservations synchronize with `stock.quant.reserved_quantity` via move-line `quantity_product_uom` and `_synchronize_quant`. Source also: https://raw.githubusercontent.com/odoo/odoo/19.0/addons/stock/models/stock_move_line.py — Accessible, 2026-07-16.
- [Fact] **Odoo 19 quantity model (no `quantity_done`):** on `stock.move`: `quantity` (computed sum of move-line quantities, `inverse='_set_quantity'`, stored) and `picked` (Boolean, "This checkbox is just indicative, it doesn't validate or generate…" [quote]); demand = `product_uom_qty` ("Demand"). `stock.move.line.quantity` = processed quantity per line; `lot_id` (m2o `stock.lot`) / `lot_name` carry lot/serial data. Source: https://raw.githubusercontent.com/odoo/odoo/19.0/addons/stock/models/stock_move.py and stock_move_line.py — Accessible, 2026-07-16. [Inference] "Delivered so far" per move = `quantity` where state `done`; demand = `product_uom_qty`.
- [Fact] **Backorders:** `stock.picking.type.create_backorder` = `ask`/`always`/`never` [quote of help]: "Ask: users are asked to choose if they want to make a backorder for remaining products * Always: a backorder is automatically created * Never: remaining products are cancelled". `_check_backorder()` flags only when `ask` and shortfall exists; `_create_backorder()` "will create a new picking, the backorder, and move the stock.moves that are not `done` or `cancel` into it" [quote], links `backorder_id`, auto-assigns when reservation `at_confirm`. Wizard `stock.backorder.confirmation`: `process()` (with backorder) vs `process_cancel_backorder()` (validates with `skip_backorder=True` — remaining demand dropped), logging shortfalls via `_check_less_quantities_than_expected()`. Source: stock_picking.py + https://raw.githubusercontent.com/odoo/odoo/19.0/addons/stock/wizard/stock_backorder_confirmation.py — Accessible, 2026-07-16.
- [Fact] **Returns:** `stock.return.picking` copies the picking with reversed locations (`_prepare_move_default_values` swaps `location_id`/`location_dest_id`) and sets `origin_returned_move_id` per return move. `to_refund` (in **stock_account**, on wizard line and `stock.move`) [quote]: "Update quantities on SO/PO … Trigger a decrease of the delivered/received quantity in the associated Sale Order/Purchase Order". `sale_stock` delivered-qty compute subtracts return moves only when `origin_returned_move_id` set and `to_refund` true. User docs [quote]: "When an invoice is created, the customer receives an invoice **only** for the products they are keeping, if any"; post-invoice refunds use credit notes. Sources: https://raw.githubusercontent.com/odoo/odoo/19.0/addons/stock/wizard/stock_picking_return.py; https://github.com/odoo/odoo/blob/19.0/addons/stock_account/wizard/stock_picking_return.py; https://www.odoo.com/documentation/19.0/applications/sales/sales/products_prices/returns.html — all Accessible, 2026-07-16. **[Fact/design consequence] Stock re-enters inventory only when the return picking is validated — exactly the accepted Odoo workflow the COD design requires (no stock restoration on courier claims).**
- [Fact] Multi-step delivery: `stock.warehouse.delivery_steps` = `ship_only` (default) / `pick_ship` / `pick_pack_ship` [quote]; warehouse auto-generates routes/rules; three-step docs confirm chained pick→pack→ship transfers each waiting on the previous. Sources: https://raw.githubusercontent.com/odoo/odoo/19.0/addons/stock/models/stock_warehouse.py; https://www.odoo.com/documentation/19.0/applications/inventory_and_mrp/inventory/shipping_receiving/daily_operations/delivery_three_steps.html — Accessible, 2026-07-16.
- [Fact] Carrier/tracking (in `stock_delivery`): `carrier_id` (m2o `delivery.carrier`) and `carrier_tracking_ref` (Char) on picking [quotes]; `send_to_shipper()` on validation sets `carrier_tracking_ref` from the carrier response, appends comma-separated refs, propagates along the move chain; `stock.rule.propagate_carrier`. Source: https://raw.githubusercontent.com/odoo/odoo/19.0/addons/stock_delivery/models/stock_picking.py — Accessible, 2026-07-16.

## 3. Quantity semantics (`product.product`)

Source: https://raw.githubusercontent.com/odoo/odoo/19.0/addons/stock/models/product.py — Accessible, 2026-07-16.

- [Fact — quotes of help strings] `qty_available` "Quantity On Hand" = "Current quantity of products…" scoped by context (single location / warehouse / all internal); `virtual_available` "Forecasted Quantity" = "Quantity On Hand - Outgoing + Incoming"; `free_qty` "Free To Use Quantity" = "Quantity On Hand - reserved quantity"; plus `incoming_qty`/`outgoing_qty` (planned moves in waiting/confirmed/assigned).
- [Fact] All five are non-stored computes over `stock.quant`/`stock.move` aggregates; **context-scoped** by `warehouse_id`, `location`, `lot_id`, `owner_id`, `package_id`, `from_date`/`to_date`, `allowed_company_ids`. Reading without a warehouse/location context aggregates across ALL internal locations — a critical per-Shopify-location sync pitfall.
- [Recommendation] Export **`free_qty` with an explicit per-mapped-location context** as Shopify "available": `qty_available` oversells (ignores reservations); `virtual_available` counts planned receipts and double-counts outgoing demand once Shopify orders import. `virtual_available` may be an explicit opt-in "sell on forecast" mode, never the default. (Consistent with accepted DEC-010 Odoo-authoritative posture.)
- [Open question] Expiry (`with_expiration`) interaction with `free_qty`/`virtual_available` observed in compute code, not user-doc verified.

## 4. Payments/AR surface relevant to COD

Sources: https://www.odoo.com/documentation/19.0/applications/finance/accounting/payments.html (Accessible); https://raw.githubusercontent.com/odoo/odoo/19.0/addons/account/models/account_move.py (Accessible); addons/sale/models/sale_order.py (Accessible); https://raw.githubusercontent.com/odoo/odoo/19.0/addons/account/wizard/account_payment_register.py (Accessible) — all 2026-07-16.

- [Fact] Payment registration: "Click Pay on a customer invoice…" [quote]; after registration the invoice is "marked as **In payment**"; only "After the invoice/bill is reconciled with a bank transaction, the invoice/bill is marked as **Paid**" [quotes]. Counterpart posts to outstanding accounts until bank reconciliation. Partial/multiple payments supported.
- [Fact] `account.move.payment_state` values: `not_paid`, `in_payment`, `partial`, `paid`, `reversed`, `blocked`, `invoicing_legacy`; `paid` requires zero residual AND full matching.
- [Fact] **`sale.order` has no payment_state of its own.** Payment visibility: `transaction_ids` (accounting-group restricted), `amount_paid` (transactions in done/authorized), `amount_to_invoice`, `amount_invoiced`, `authorized_transaction_ids`. [Inference] Order-level "COD collected?" must be derived from linked invoices' `payment_state` and/or `payment.transaction` — or carried by connector-owned fields.
- [Fact] `account.payment.register.action_create_payments()` creates payments, **immediately posts them** (`_post_payments()` → `action_post()`) and **auto-reconciles**; behavior depends on `journal_id`, `payment_method_line_id`, `group_payment`, `payment_difference_handling`, currency, partner bank. [Recommendation] A connector must not silently invoke this wizard: posted, reconciled journal entries with guessed journals/write-offs are auditable financial records requiring reversal to undo. Default = operational COD visibility on connector records; accounting posting only behind explicit Administrator configuration. (This grounds the mission's binding accounting boundary.)
- [Open question] Whether a built-in COD payment provider (`payment_custom`) populates `amount_paid` — unverified.

## 5. Security model (groups, ACLs, rules, field groups)

Sources: https://raw.githubusercontent.com/odoo/odoo/19.0/odoo/addons/base/models/res_groups.py; res_users.py; res_groups_privilege.py; https://raw.githubusercontent.com/odoo/documentation/19.0/content/developer/reference/backend/security.rst; …/tutorials/restrict_data_access.rst; …/reference/backend/data.rst — all Accessible, 2026-07-16 (rendered odoo.com pages Partial/nav-only to the fetcher).

- [Fact] `res.groups.implied_ids` [quote]: "Users of this group are also implicitly part of those groups"; computed transitive closure `all_implied_ids` ("Compute the reflexive transitive closure of implied_ids." [quote]). Docs [quote]: "it's possible to explicitly remove implied groups from a user without removing the implier." Set semantics [quote excerpt]: "A manager group will imply a user group: all managers are users…" — **exactly the Administrator-implies-User mechanism the two-role model needs.**
- [Fact] Odoo 19 rework: `res.users.group_ids` ("Groups explicitly assigned to the user") + computed `all_group_ids` ("Groups and implied groups") with `user.all_group_ids = user.group_ids.all_implied_ids`.
- [Fact] **New in 19: `res.groups.privilege`** (name, sequence, `category_id` → `ir.module.category`, `group_ids`, description, `placeholder` — help [quote]: "Text that is displayed as placeholder in the selection field of the user form."); `res.groups.privilege_id` links groups to a privilege. [Inference] Groups sharing one `privilege_id` render as ONE selection field per privilege on the user form — the sanctioned way to show "Connector role: User | Administrator" as a single dropdown. [Open question OQ-1] Exact radio-vs-checkbox rendering rule to verify in `res_users_views.xml` before the migration packet is implemented.
- [Fact] ACLs [quote]: "Access rights are additive… the user will have all three of create, read, and update." `group_id` optional (global); "Access rights can only give access, they can't remove it." [quote].
- [Fact] Record rules [quote]: "Global rules intersect… Group rules unify… The global and group rulesets intersect."
- [Fact] Field-level `groups=` [quote]: "restricted fields are automatically removed from requested views; … removed from fields_get responses; attempts to (explicitly) read from or write to restricted fields results in an access error." View/menu `groups` = visibility only, not security (tutorial). [Recommendation] Sensitive connector fields must keep Python-level `groups=`.
- [Fact] XML ID stability: external IDs let "subsequent definitions … either modify or refer to this record" [quote]; `noupdate=1` data "Only loaded when installing the module" [quote]; normal data "(Re)Loaded at install and update" [quote]. [Inference] Group definition changes propagate on upgrade only without noupdate; renaming a group XML ID is delete+create — the two-role migration must keep stable XML IDs and never rename the existing four. [Open question OQ-3] Upgrade-time deletion of records whose XML IDs are removed from data files — verify `ir_model_data` cleanup code before packet implementation.

## 6. ir.cron and Odoo.sh constraints

Sources: https://raw.githubusercontent.com/odoo/odoo/19.0/odoo/addons/base/models/ir_cron.py; https://raw.githubusercontent.com/odoo/documentation/19.0/content/developer/reference/backend/actions.rst; …/administration/odoo_sh/advanced/frequent_technical_questions.rst; …/administration/odoo_sh/getting_started/branches.rst — all Accessible (raw), 2026-07-16.

- [Fact] Fields: `interval_number`/`interval_type` (minutes/hours/days/weeks/months), `nextcall`, `active`, `priority` (0–10, "0 means higher priority" [quote]), `lastcall` ("Previous time the cron ran successfully…" [quote]), failure tracking `failure_count` ("automatically reset on success" [quote]) + `first_failure_date`.
- [Fact] Locking: `_acquire_one_job` uses `FOR NO KEY UPDATE SKIP LOCKED` [quote] — "two cron workers cannot process a given job at a same time" [source-comment quote].
- [Fact] Triggers: `ir.cron.trigger` (`cron_id`, indexed `call_at`); `_trigger()` docstring [quote]: "Schedule a cron job to be executed soon independently of its `nextcall` field value."; `_notifydb()` wakes workers; GC after one week.
- [Fact] Failure handling: exceptions roll back; deactivation when `failure_count >= 5` and first failure ≥ 7 days old (`MIN_FAILURE_COUNT_BEFORE_DEACTIVATION = 5`, `MIN_DELTA_BEFORE_DEACTIVATION = timedelta(days=7)`, `CONSECUTIVE_TIMEOUT_FOR_FAILURE = 3`); admin notified ("Cron job … has been deactivated after failing 5 times." [quote]). **[Design consequence] A repeatedly-failing connector cron can be auto-disabled — dashboards must surface cron health, and the drain cron must never let handler failures escape as cron failures.**
- [Fact] Missed executions: `_reschedule_later()` advances `nextcall` past now — missed intervals are NOT replayed individually.
- [Fact] Long jobs: docs [quote] — batches "should generally take no more than *a few seconds*"; **`_commit_progress(processed, remaining=…)`** is the 19.0 API (returns "remaining time (seconds) for the cron run" [quote]; return when zero); `_notify_progress()` deprecated; `_run_job()` caps at `MIN_RUNS_PER_JOB = 10` / `MIN_TIME_PER_JOB = 10`s with FULLY_DONE/PARTIALLY_DONE/FAILED statuses. (PERF-1's `_commit_progress()` rework premise is confirmed.)
- [Fact] Odoo.sh [quotes]: "we cannot guarantee an exact running time for scheduled actions"; "Do not expect any scheduled action to be run more often than every 5 min."; "Odoo.sh always limits the execution time of scheduled actions" (exceeded jobs interrupted → commit per batch, idempotent design). Staging: "The neutralization disables: Scheduled actions" (manual trigger/re-enable; less often when DB unused). Dev branches: crons not triggered while DB not in use.
- [Open question] Numeric Odoo.sh cron time limit / worker counts per plan — not published. [Open question] No explicit official "never call cr.commit()" sentence for 19 — docs channel everything through `_commit_progress()` (treat raw commits as discouraged).

## 7. Module lifecycle

Sources: https://raw.githubusercontent.com/odoo/documentation/19.0/content/developer/reference/backend/module.rst; data.rst; …/reference/upgrades/upgrade_scripts.rst; https://raw.githubusercontent.com/odoo/odoo/19.0/odoo/modules/module.py; odoo/addons/base/models/ir_module.py; ir_model.py — all Accessible, 2026-07-16.

- [Fact] Hooks take `env` in 19: `pre_init_hook` ("executed prior to the module's installation" [quote]), `post_init_hook` ("right after" [quote]), `uninstall_hook` ("after the module's uninstallation" [quote]). `post_load` is source-verified, called at Python-load time with no args (undocumented internal).
- [Fact] `noupdate=1` records load only at install; `forcecreate` defaults True.
- [Fact] **Uninstall drops structures:** `_module_data_uninstall` deletes all module-owned xml-id records; `IrModelFields.unlink()` → `ALTER TABLE … DROP COLUMN … CASCADE`; m2m rel tables and model tables get `DROP TABLE … CASCADE`; constraints dropped. Copied views without external ids are separately removed (`_remove_copied_views` [quote of comment]). **[Design consequence] Uninstalling a connector module hard-deletes its models/columns — DEC-030's export-before-uninstall step and the retention design must account for this.**
- [Fact] Migration scripts: `$module/migrations/$version/` (or `upgrades/`), `{pre|post|end}-*.py`, phases quoted (pre "before the module is loaded"; post "after the module and its dependencies are loaded and updated"; end "after all modules"), signature `migrate(cr, version)` (cursor, not env).
- [Open question] Official 19.0 way to force-update noupdate records (use migration scripts — Recommendation). [Open question] Exact uninstall_hook call site.
