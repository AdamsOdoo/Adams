| SRR-01 | Per-record savepoint isolation (already an accepted DEC-005 requirement) could degrade PostgreSQL performance if a batch loop grows large, per Odoo's own documented warning. | `O8` (official Odoo coding guidelines, direct quote): "After you start more than 64 savepoints during a single transaction, PostgreSQL will slow down... if you have more records, the function should maybe become a scheduled job or you have to accept the performance penalty." Independently corroborated by `R31` (PR #124, same source, same quote). | Medium likelihood at realistic catalog/order volumes if batch size is not explicitly capped; severity Medium (performance degradation, not data loss) — worse on replicated deployments per the same source. **This is a documented performance warning, not a hard functional cap** — nothing in either shard's research found the framework enforcing this number in code; `R31` additionally found core `create()`/`write()` do not savepoint automatically by default. | A cron batch processing more than ~64 records with one savepoint each in a single transaction. | Cap per-transaction savepoint count well below 64, or restructure to multiple smaller cron invocations (the framework's own `_commit_progress`/batching mechanism already exists for this, `O7`). `R33` (PR #126) independently researched PostgreSQL locking more broadly and adds a related consideration: advisory locks (`pg_advisory_lock`) are an alternative primitive with their own hazards (see SRR-09) — worth weighing alongside the savepoint-batching mitigation, not a substitute for it. | Architecture-gate / implementation-planning — this numeric input was not in prior repo research before this session and `R31`; `R33` independently corroborates the same source and quote. |
| SRR-02 | Retry logic implemented independently at multiple layers (e.g. GraphQL client retry + cron batch retry + operator manual retry) could amplify load against Shopify's own rate limits during an incident, worsening rather than resolving it. | `E2` (AWS Builders' Library, worked example: 5-layer stack × 3 retries/layer → 243x load amplification); `E3` (Google SRE book, worked example: retried QPS compounding turn-over-turn). | Low likelihood if retry is deliberately centralized (as DEC-005/DEC-009 already intend); severity High if it occurs, since it would degrade Shopify API access for the whole connected store during an outage. | Uncoordinated/duplicated retry logic added at more than one layer without a shared budget or single point of control. | Concentrate retry logic at one layer (the job/state-machine layer, which already exists, `R1`) rather than also retrying inside the low-level API client; consider a Google-SRE-style retry budget if/when implemented. | Implementation-planning — already directionally consistent with the accepted design (`R11` §9 already uses jittered backoff at the job layer), flagged as a risk to guard against during implementation, not a gap in current planning. |
| SRR-03 | A business job could remain in `running` state through an in-flight `ir.cron` batch at the exact moment a store is disconnected, potentially completing a live Shopify write against a now-disconnected/unverified credential. | **RUNTIME-CONFIRMED as DEF-PB-1 (PR #153, control-room accepted `4950408383`).** With the real merged `store.action_disconnect()`, the disconnect **blocks behind the running job's row lock**, the handler **completes**, the job **succeeds**, and the disconnect then serialization-fails (library) or is retried by `retrying()` and completes cancelling **zero** running jobs (`sync-engine-concurrency-validation-results.md` §10/§14; `evidence/sync-engine-concurrency/scenario-06-real-timeline.md`). Source root cause: the drain runs one REPEATABLE READ transaction (`odoo/sql_db.py:373`), so checkpoint-3's store re-check is snapshot-blind. Earlier framing that `R3`/`R1` gating "narrows" the race is confirmed insufficient. | Confirmed real (no longer "unknown"); latent **only** because every shipped handler is a no-op — becomes a live-write defect the moment a domain handler performs a real Shopify mutation. Severity High. | A store disconnect executing concurrently with an already-`running` business job for that same store. | **Remediation now DESIGNED (not implemented): CORE-R2 (rev 4, review `4680299311`) — INV-2 enforced at an explicit `execute_business(job, …)` boundary on the central API client, fail-closed against a persisted connection epoch (`store.connection_generation` vs enqueue-captured `job.expected_connection_generation`); admission is made ATOMIC with disconnect by a store-row LOCK protocol — admission holds `FOR SHARE` while it reads state/epoch, reads the token once, and commits the lease; every generation-changing lifecycle transition takes the conflicting `FOR NO KEY UPDATE`/`FOR UPDATE` (the lock, not the bare lease commit, is the linearization point); `execute_business` is a CONTEXT MANAGER whose protected lifetime wraps the HTTP call AND its local reconciliation (no early/forgotten release); `execute_lifecycle(purpose=…)` (plain, no lease) for setup/diagnostic calls; INV-3 (quiescence) proven by a COMMITTED admission-lease (`shopify.connector.call.lease`) — NOT a `running` count (invisible cross-transaction because `run_drain` runs `running`→handler→terminal in one uncommitted transaction) — under DIRECTION C: an expired-but-unreleased lease is unknown/live, `completed` requires zero lease rows, a crashed holder resolves via a distinct `timed_out` finalize (cleanup only afterward), so a slow-but-live reconciliation is never falsely drained; single in-memory token snapshot passed to `_send`; one-store-per-cron-invocation controller selecting via `try_lock_for_update(limit=1)` (`FOR UPDATE SKIP LOCKED LIMIT 1`, picks the next unlocked store) with a bounded `POLL_DELAY` cadence via delayed `_trigger(at=…)` (no busy loop); lease-based timeout escalation on store fields (never the locked job row); ordered rollback requiring ZERO holders (workers drained first) before code/model removal; advisory lock stays DROPPED** (`../03-architecture/disconnect-quiescence-remediation-analysis.md`; packet `../07-implementation-plan/task-core-r2-disconnect-quiescence-packet.md`). Proposed for ChatGPT review; the CORE-R2 code gate is **not** open. | **OPEN.** Runtime-confirmed; remediation designed under the CORE-R2 gate (PR #153 comment `4950413650`, rev 4 per `4680299311`; base re-aligned to `cfdb057`), **implementation gate not opened**. Because the defect applies to **any Shopify call including reads**, the fix must be proven live (Odoo.sh + genuine two-server test) **before merging/enabling/live-validating any domain handler that calls Shopify** — 010B/011B/012 live validation and Tasks 013–015 — and before UAT; parallel development of those tasks is allowed. Stays OPEN until the CORE-R2 fix merges runtime-green. |
| SRR-04 | Whether Odoo's own RPC-layer automatic serialization-conflict retry (`retrying()`) protects a cron job's own record-processing code is unconfirmed — if it does not, a future sync-engine cron batch could hit an unhandled `SerializationFailure`/`LockNotAvailable`/`DeadlockDetected` and simply fail the batch rather than safely retrying. | `O5`, `O6` (source-confirmed: `retrying()` wraps RPC/HTTP dispatch); `O7` (`ir.cron._callback()` has no equivalent found in the code reviewed — confirmed absent by grep of `ir_cron.py`); `R31` (PR #124, independently examined the related but distinct job-*acquisition* layer — `_acquire_one_job`'s `FOR NO KEY UPDATE SKIP LOCKED` and `_process_jobs_loop`'s rollback-and-continue on `SerializationFailure` — without settling the domain-record-processing question); `R33` (PR #126, a **third** shard, states the same open-question framing even more explicitly and additionally names a related multi-server-coordination question, see SRR-09). | Medium likelihood once multiple cron workers process overlapping record sets concurrently (`--max-cron-threads` default 2, already known); severity Medium (a failed batch is visible and re-runnable via the existing `failed_final`/retry surface, not silent data loss). **This risk rests on a source-backed inference, not a proven fact — now corroborated by three independently-produced research shards** reaching the same open-question framing, which strengthens confidence the question is real and worth resolving, without itself proving the underlying risk materializes. | Two concurrent cron-worker batches touching the same underlying domain record (e.g. two sync jobs for the same product); or two Odoo application servers sharing one PostgreSQL database (a distinct, multi-server variant of this risk `R33` names, see SRR-09). | Explicit use of `lock_for_update()`/`try_lock_for_update()` (`O9`, independently confirmed by `R31` and `R33`) and/or the connector's own catch-rollback-retry logic inside job handlers, mirroring the official cron-writing guide's own worked example (`O13`) — a plausible mitigation *if* the underlying inference is confirmed, not a settled requirement. `try_lock_for_update`/`lock_for_update` are now source-confirmed to issue `… FOR UPDATE SKIP LOCKED` and to be non-blocking (`odoo/orm/models.py:5564`/`5592`); `retrying()` is source-confirmed to retry `(LockNotAvailable, SerializationFailure, DeadlockDetected)` up to 5 tries at the RPC boundary (`odoo/service/model.py:160`). | **REDUCED, not closed (PR #153, `4950408383`).** Genuine process-level (B-like) and two-instance (Topology C, single host) evidence showed disjoint claims, no double-processing, no deadlock — but no deployed multi-`--workers` server and no sustained load were exercised. Architecture-gate / implementation-planning — informs the future job-drain-loop design and the CORE-R2 disconnect coordination (which deliberately avoids adding any `NOWAIT`/raw `FOR UPDATE` on the job row); remains open for deployed-multi-worker + sustained-load proof. |
| SRR-05 | Odoo core's `ir.cron` failure-notification path (`_notify_admin`) is a no-op logger call by default — an operator could believe a deactivated scheduled action would alert them, when in base Odoo it will not. | `O7` (direct quote: `_notify_admin`'s "base implementation of this method does nothing... supposed to be overridden with some actual communication mechanism"; base behavior is `_logger.warning(message)` only). `R33` (PR #126) independently researched dead-letter/failure visibility more broadly and found the identical pattern holds across every commercial DLQ implementation examined: visibility is an opt-in, separately-wired alarm/metric, never a default push notification (`R33`'s Dead-letter notes, citing AWS/Azure). | Low likelihood of direct harm (this repo's own job/log dashboard, already implemented, is the real operator-visible surface — not `ir.cron`'s notify step) but worth flagging so no future design mistakenly relies on `ir.cron`'s own notification as sufficient. `R33`'s broader finding sharpens this: even this repo's own job/log dashboard captures *state*, but whether an alarm/dashboard is actively wired to surface it to an operator is a distinct question this package has not evaluated. | A scheduled action deactivates after 5 failures over ≥7 days, and no code overrides `_notify_admin`; more broadly, any dead-lettered/`failed_final` job that exists in storage but has no alarm/dashboard actively wired to it. | None required if the sync engine continues to treat its own job/log/error-center surface (already accepted, DEC-005) as the operator-visible failure signal rather than `ir.cron`'s admin-notify step — restated here as a documented assumption to keep true, not a new gap. Whether that surface has an actual alarm/dashboard wired to it (per `R33`'s "opt-in, not automatic" finding) is worth confirming at a future UX/observability design pass. | Observability design confirmation — low priority. |
| SRR-06 | Repeating the PR #121 failure pattern: a concurrency/timing-dependent defect that passes every static and adversarial review but only manifests under live Odoo.sh execution. | `R18` (Task 005 validation results — `credential.write_date` freshness-guard brittleness passed `py_compile` and three prior PR revisions' review, failed 5 tests live); `DEC-024` §4 "Lessons learned" (`R18`, cited): "Any future freshness guard comparing an ORM-managed timestamp field... against a manually-stamped field should be treated as requiring actual Odoo-runtime validation before being trusted." | Medium likelihood for *any* concurrency-sensitive sync-engine mechanism (locking, savepoint batching, cron-worker job acquisition) given this project's own direct precedent; severity High if it recurs (a runtime failure discovered only after significant implementation effort). | Any future concurrency/locking/timing-dependent mechanism design and implementation that is validated only statically (`py_compile`, code review) before being merged. | Mandatory live Odoo.sh validation (not merely static review) for any future sync-engine implementation task touching concurrency, locking, or savepoint batching — consistent with this project's own existing practice for Tasks 001–005. | Process/governance reminder for the future implementation-gate acceptance criteria — not a new architecture question, a restatement of an already-learned lesson applied specifically to sync-engine concurrency design. |
| SRR-07 | Bulk operations' recovery model (whole-operation resubmission only, no documented partial-resume) is a weaker fit for resumability than cursor pagination, and this trade-off could be overlooked if bulk operations are later adopted for first-sync product import without re-examining it. | `S7`, `S8` (Shopify's own wording for both cancellation-recovery and timeout-recovery: "submitting the query again," no partial-resume mechanism described); independently corroborated by `R33` (PR #126, same conclusion via a separate fetch of the same pages). | Low likelihood of near-term harm (bulk operations are not currently adopted, `R7` DEC-005); severity Medium if adopted later without accounting for this — a large first-sync import that fails late could require a full, expensive re-run rather than a cheap resume. | A future decision to adopt bulk operations for large first-sync imports, without designing for the all-or-nothing recovery model. | Weigh this trade-off explicitly against cursor pagination's finer-grained (but also unconfirmed-durability) checkpoint story when/if a first-sync-import architecture is designed. | Domain-module (product-import) architecture task — informed by, not decided by, this research. |
| SRR-08 | A throttled Shopify **GraphQL** call can return HTTP 200 with a `THROTTLED` code in the response body rather than a 4xx status — a client written against REST's 429-based mental model, checking only HTTP status, would silently treat a throttled GraphQL call as successful. | `R33` (PR #126, `SH-4`, new this revision — this package's own pre-006A rate-limit baseline had not independently verified GraphQL throttle response-status behavior). | Medium-High likelihood if the sync engine's GraphQL client is modeled on REST-style status-code branching without an explicit body-level check; severity Medium-High if it occurs — a silently-dropped/miscounted throttled call could look like a successful no-op, masking real sync gaps. | Any GraphQL call whose response-handling code checks only HTTP status, not the response body, for throttle signals. | The response-parsing layer must inspect the GraphQL response body for a `THROTTLED` error code on every call, not rely on HTTP status alone. No documented `Retry-After`-equivalent exists for this case; fallback is deriving a wait time from `throttleStatus`. | Architecture-gate / implementation-planning — a concrete, actionable design requirement for the future GraphQL client layer, not previously surfaced by this package. |
| SRR-09 | Whether `ir.cron`'s row-lock-only (`FOR NO KEY UPDATE SKIP LOCKED`) job-acquisition approach is sufficient with no additional cross-server coordination when multiple Odoo application servers share one PostgreSQL database is unconfirmed; separately, PostgreSQL advisory locks (an alternative/complementary primitive) carry their own non-obvious hazards if considered for a future job-claiming design. | `R33` (PR #126, new this revision): names the multi-server question as "a real operational pain point worth an explicit runtime test," citing a historical GitHub issue about load-balanced cron scheduling as circumstantial evidence; separately documents PostgreSQL's own "danger!" example where an advisory-lock call inside `SELECT ... ORDER BY ... LIMIT` can lock rows before `LIMIT` applies, and that session-scoped advisory locks are not released by a transaction rollback (`GEN-30`, `GEN-31`). | Unknown likelihood for the multi-server question (no source proves or disproves it for this project's actual deployment topology); severity potentially High if it occurs on a load-balanced/multi-server Odoo.sh or on-prem deployment (duplicate job execution across servers). Advisory-lock hazards are only relevant if that primitive is chosen — not currently in use anywhere in this repo. | A future multi-server/load-balanced Odoo deployment running the sync engine's cron jobs; or a future design choosing PostgreSQL advisory locks without accounting for the `LIMIT`-ordering and session-persistence hazards. | Requires an actual multi-server concurrency test before this can move from "risk" to "confirmed defect" or "confirmed non-issue" (not resolvable by source-reading alone, per `R33`'s own framing). If advisory locks are ever considered, use the transaction-scoped variant (`pg_advisory_xact_lock`) and avoid combining with `LIMIT`-bounded queries per the documented hazard. | **REDUCED (single-host two-instance evidence only), not closed (PR #153, `4950408383`).** The multi-server coordination question is exercised only single-host (Topology C); true multi-node/Odoo.sh remains open. The CORE-R2 disconnect-quiescence design (rev 4, review `4680299311`) **evaluated a shared/exclusive `pg_advisory_xact_lock` quiescence barrier and REJECTED it** in favour of a **committed admission-lease record** (`shopify.connector.call.lease`, side-cursor committed before each Shopify call, released in the context-manager exit after local reconciliation, direction-C expiry handling for crash recovery): the lease is independently visible cross-transaction (unlike uncommitted `running` state), gives the escalation surface a real holder count/timestamps (which a bare advisory lock cannot), and costs two short side-transactions per call instead of holding a connection open for the whole call (`../03-architecture/disconnect-quiescence-remediation-analysis.md` §10, packet §7). The disconnect call race itself is closed by the epoch gate at `execute_business` **serialized by a native store-row `FOR SHARE`/`FOR NO KEY UPDATE` lock** (not an advisory lock); the advisory lock stays dropped (if ever needed elsewhere, only the bounded `pg_try_advisory_xact_lock`, namespaced, released at txn end, never inside a `LIMIT` query). **Still requires live multi-server proof** for the coordination question. |
