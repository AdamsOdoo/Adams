# Sync Engine — Risk Register (Task 006A)

> Risk-focused supplement to
> [`sync-engine-open-questions.md`](./sync-engine-open-questions.md).
> Created because several findings from this session's research are more
> naturally framed as **risks with evidence** (a specific failure mode, a
> cited mechanism, a plausible trigger) than as open questions. Research
> only — no architecture decision, no implementation, no mitigation is
> authorized or selected here; "mitigation direction" columns describe what
> the evidence suggests is *worth evaluating*, not a decision.
>
> **Revision note:** this branch was updated against latest
> `Shopify-connector` after PR #123 and PR #124 merged. SRR-01 and SRR-04
> below were reworded this revision to correct overclaim/overstated-certainty
> wording flagged by control-room review, and are now cross-referenced
> against `docs/01-research/sync-engine-odoo-repo-source-notes.md` (PR #124,
> `R31`), the canonical Odoo/repo-substrate shard for this task family.

| ID | Risk | Evidence | Likelihood / severity (qualitative) | Trigger condition | Mitigation direction (not decided) | Owner / next step |
| --- | --- | --- | --- | --- | --- | --- |
| SRR-01 | Per-record savepoint isolation (already an accepted DEC-005 requirement) could degrade PostgreSQL performance if a batch loop grows large, per Odoo's own documented warning. | `O8` (official Odoo coding guidelines, direct quote): "After you start more than 64 savepoints during a single transaction, PostgreSQL will slow down... if you have more records, the function should maybe become a scheduled job or you have to accept the performance penalty." Independently corroborated by `R31` (PR #124, same source, same quote). | Medium likelihood at realistic catalog/order volumes if batch size is not explicitly capped; severity Medium (performance degradation, not data loss) — worse on replicated deployments per the same source. **This is a documented performance warning, not a hard functional cap** — nothing in either shard's research found the framework enforcing this number in code; `R31` additionally found core `create()`/`write()` do not savepoint automatically by default. | A cron batch processing more than ~64 records with one savepoint each in a single transaction. | Cap per-transaction savepoint count well below 64, or restructure to multiple smaller cron invocations (the framework's own `_commit_progress`/batching mechanism already exists for this, `O7`). | Architecture-gate / implementation-planning — this numeric input was not in prior repo research before this session and `R31`. |
| SRR-02 | Retry logic implemented independently at multiple layers (e.g. GraphQL client retry + cron batch retry + operator manual retry) could amplify load against Shopify's own rate limits during an incident, worsening rather than resolving it. | `E2` (AWS Builders' Library, worked example: 5-layer stack × 3 retries/layer → 243x load amplification); `E3` (Google SRE book, worked example: retried QPS compounding turn-over-turn). | Low likelihood if retry is deliberately centralized (as DEC-005/DEC-009 already intend); severity High if it occurs, since it would degrade Shopify API access for the whole connected store during an outage. | Uncoordinated/duplicated retry logic added at more than one layer without a shared budget or single point of control. | Concentrate retry logic at one layer (the job/state-machine layer, which already exists, `R1`) rather than also retrying inside the low-level API client; consider a Google-SRE-style retry budget if/when implemented. | Implementation-planning — already directionally consistent with the accepted design (`R11` §9 already uses jittered backoff at the job layer), flagged as a risk to guard against during implementation, not a gap in current planning. |
| SRR-03 | A business job could remain in `running` state through an in-flight `ir.cron` batch at the exact moment a store is disconnected, potentially completing a live Shopify write against a now-disconnected/unverified credential. | `R3` (`action_disconnect()` cancels only non-terminal jobs at the moment it runs); Task-005 execution-time gate (`R1`) blocks a transition *into* `running` but does not interrupt a job already past that check. Neither this package nor `R31` (PR #124, which independently inspected the same substrate) proves or disproves this race in practice. | Unknown likelihood — no source proves or disproves this race occurs in practice; severity potentially High if it does (a write against a credential the operator believed was cleared). | A store disconnect action executing concurrently with an already-`running` business job for that same store. | Requires live Odoo-runtime investigation (concurrent worker timing) before any mitigation can be scoped — premature to design a fix without first confirming the race is real. | **Requires live Odoo.sh proof** (see open-questions §"Questions that require live Odoo.sh proof", item 30) before this can move from "risk" to "confirmed defect" or "confirmed non-issue." |
| SRR-04 | Whether Odoo's own RPC-layer automatic serialization-conflict retry (`retrying()`) protects a cron job's own record-processing code is unconfirmed — if it does not, a future sync-engine cron batch could hit an unhandled `SerializationFailure`/`LockNotAvailable`/`DeadlockDetected` and simply fail the batch rather than safely retrying. | `O5`, `O6` (source-confirmed: `retrying()` wraps RPC/HTTP dispatch); `O7` (`ir.cron._callback()` has no equivalent found in the code reviewed — confirmed absent by grep of `ir_cron.py`); `R31` (PR #124, independently examined the related but distinct job-*acquisition* layer — `_acquire_one_job`'s `FOR NO KEY UPDATE SKIP LOCKED` and `_process_jobs_loop`'s rollback-and-continue on `SerializationFailure` — without settling the domain-record-processing question). | Medium likelihood once multiple cron workers process overlapping record sets concurrently (`--max-cron-threads` default 2, already known); severity Medium (a failed batch is visible and re-runnable via the existing `failed_final`/retry surface, not silent data loss). **This risk rests on a source-backed inference, not a proven fact** — requires runtime proof before treating as confirmed. | Two concurrent cron-worker batches touching the same underlying domain record (e.g. two sync jobs for the same product). | Explicit use of `lock_for_update()`/`try_lock_for_update()` (`O9`, independently confirmed by `R31`) and/or the connector's own catch-rollback-retry logic inside job handlers, mirroring the official cron-writing guide's own worked example (`O13`) — a plausible mitigation *if* the underlying inference is confirmed, not a settled requirement. | Architecture-gate / implementation-planning — directly informs the future job-drain-loop design (see SRR-\* interplay with Blocking Question 5 in open-questions.md). |
| SRR-05 | Odoo core's `ir.cron` failure-notification path (`_notify_admin`) is a no-op logger call by default — an operator could believe a deactivated scheduled action would alert them, when in base Odoo it will not. | `O7` (direct quote: `_notify_admin`'s "base implementation of this method does nothing... supposed to be overridden with some actual communication mechanism"; base behavior is `_logger.warning(message)` only). | Low likelihood of direct harm (this repo's own job/log dashboard, already implemented, is the real operator-visible surface — not `ir.cron`'s notify step) but worth flagging so no future design mistakenly relies on `ir.cron`'s own notification as sufficient. | A scheduled action deactivates after 5 failures over ≥7 days, and no code overrides `_notify_admin`. | None required if the sync engine continues to treat its own job/log/error-center surface (already accepted, DEC-005) as the operator-visible failure signal rather than `ir.cron`'s admin-notify step — restated here as a documented assumption to keep true, not a new gap. | Observability design confirmation — low priority. |
| SRR-06 | Repeating the PR #121 failure pattern: a concurrency/timing-dependent defect that passes every static and adversarial review but only manifests under live Odoo.sh execution. | `R18` (Task 005 validation results — `credential.write_date` freshness-guard brittleness passed `py_compile` and three prior PR revisions' review, failed 5 tests live); `DEC-024` §4 "Lessons learned" (`R18`, cited): "Any future freshness guard comparing an ORM-managed timestamp field... against a manually-stamped field should be treated as requiring actual Odoo-runtime validation before being trusted." | Medium likelihood for *any* concurrency-sensitive sync-engine mechanism (locking, savepoint batching, cron-worker job acquisition) given this project's own direct precedent; severity High if it recurs (a runtime failure discovered only after significant implementation effort). | Any future concurrency/locking/timing-dependent mechanism design and implementation that is validated only statically (`py_compile`, code review) before being merged. | Mandatory live Odoo.sh validation (not merely static review) for any future sync-engine implementation task touching concurrency, locking, or savepoint batching — consistent with this project's own existing practice for Tasks 001–005. | Process/governance reminder for the future implementation-gate acceptance criteria — not a new architecture question, a restatement of an already-learned lesson applied specifically to sync-engine concurrency design. |
| SRR-07 | Bulk operations' recovery model (whole-operation resubmission only, no documented partial-resume) is a weaker fit for resumability than cursor pagination, and this trade-off could be overlooked if bulk operations are later adopted for first-sync product import without re-examining it. | `S7`, `S8` (Shopify's own wording for both cancellation-recovery and timeout-recovery: "submitting the query again," no partial-resume mechanism described). | Low likelihood of near-term harm (bulk operations are not currently adopted, `R7` DEC-005); severity Medium if adopted later without accounting for this — a large first-sync import that fails late could require a full, expensive re-run rather than a cheap resume. | A future decision to adopt bulk operations for large first-sync imports, without designing for the all-or-nothing recovery model. | Weigh this trade-off explicitly against cursor pagination's finer-grained (but also unconfirmed-durability) checkpoint story when/if a first-sync-import architecture is designed. | Domain-module (product-import) architecture task — informed by, not decided by, this research. |
