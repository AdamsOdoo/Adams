### (a) Dependencies that block ALL domain work

These four must exist (merged, gate-opened, reviewed) before **any** domain module (product, sale/customer/order, inventory, fulfillment) can safely enqueue or execute a real operation against Shopify or Odoo business data:

- **Task 002** — without stored/redacted credentials, no domain job can authenticate at all.
- **Task 003** — per the accepted single API-client boundary (DEC-008; DEC-004; RA-013), domain modules "never construct requests, read credentials, or parse raw errors themselves" — they call Shopify only through `shopify.connector.api.client` via registered job handlers. No domain sync logic can execute a real Shopify call until Task 003's gate opens.
- **Task 004** — the readiness engine determines the essential/warning tiers (MBQ-06) that gate whether a store may run business sync at all; domain sync jobs depend on this substrate to be safely enqueued.
- **Task 005** — store-state gating (`setup_incomplete` / `reconnect_needed` / `disconnected`) determines whether business sync/write jobs are enqueueable at all, per the accepted rule that "no business sync/write job is enqueueable-to-run for a store whose setup is incomplete," enforced "in the queue substrate ... at enqueue time and again at execution time" (`master-blueprint-core-substrate.md` §E.5, cited in `credential-connection-api-client-planning.md`).

### (b) Dependencies that only block UI

- **Task 006** (setup wizard UI) and, more broadly, **the UI implementation gate** it sits inside of — this gate is a separate act from the four items above. The research notes show a documented precedent ("Task 001") of core backend scaffolding (six data models, no views/menus/actions) being authorized ahead of any UI under its own narrower "core-only, zero-UI" gate. By that precedent, a domain module's backend logic is not, in principle, structurally required to wait for the UI gate — but the UI-UX research notes are explicit that **no document states a general policy on this**: *"No document in this set contains a general, explicit policy statement such as 'backend sync logic may be built before its UI' or 'UI and backend must be gated together' as an abstract rule."* This should be read as **Open — not yet decided in the repo**, not as an established sequencing rule. What is decided: every domain screen group (product, customer/matching, order-touchpoint, inventory, fulfillment screens — task-map Groups 10–14) lists the UI implementation gate as a **universal** prerequisite alongside its own named "domain gate," so domain **screens** specifically cannot ship without the UI gate.

### (c) Dependencies that only block API execution (outbound Shopify calls)

- **Task 003 specifically**, isolated from Task 002/004/005: it is the point at which *"for the first time"* outbound Shopify Admin API calls (read-only at first) are authorized. Tasks 004 and 005 consume Task 003's output (test connection result, scope snapshot) but do not themselves grant new API-call authority. Until Task 003's own gate opens, no domain job handler can perform any outbound Shopify call — read or write — regardless of what other domain-specific planning or model-definition work might otherwise be permissible.

### 1. Product import / variant binding

- **Why this position:** `shopify_connector_sale` and (later) `inventory` resolve product/variant bindings *through* `product` rather than duplicating matching logic ("sibling reuse via `product`," Part A §K.9). Order-line creation is structurally blocked without a resolved product-variant binding (the whole-order-hold rule, Part B §C.5). Product must therefore exist before order import (Area 3) and before inventory's per-location identity keying (Area 4) can be exercised meaningfully.
- **Dependencies:** `shopify_connector_product` module; the core abstract binding contract, extended as two **separate** concrete models — product-template binding and product-variant binding (Part B §A.1, §A.7); Foundation Tasks 002–005 (section above); a not-yet-defined "product domain gate" referenced as a prerequisite in `ui-ux-implementation-task-map.md` Group 10, whose own triggering conditions are not specified in any research note read for this pass.
- **Risks:** destructive-write guard risk from `productSet`'s delete-on-omit behavior, requiring a variant-level (not template-level) diff (Part B §A.7); Group 10 is rated risk "**High**" in the task map ("destructive catalog writes"); `productVariantsBulkUpdate`/`productSet`/`productVariantsBulkCreate` are **not documented to have** an idempotency guarantee (Part B §A.5.2), so ambiguous-outcome handling is required.
- **Open MBQs:** MBQ-01/02/55 (exact Odoo model/field names for the product-template and product-variant binding models — open; the open-questions register states MBQ-55 "blocks every domain slice, not the core gate," requiring "a dedicated, documentation-only domain naming/schema planning pass ... before the product/customer/order slice starts"); MBQ-23 (variant-write mutation strategy, partially resolved — direction accepted, exact batching/error-handling open); MBQ-24 (whether `productSet`'s delete-on-omit behavior extends to media, carried forward, open, inconclusive per official-doc check).
- **User value:** foundational — no order line, inventory quantity, or fulfillment line item can be resolved to a Shopify catalog entity without it.
- **Testing complexity:** Medium-high — variant-level diff correctness, the MBQ-59 pre-create duplicate-check/two-tier gate, ambiguous-match manual-review routing, and destructive-write guard behavior all need dedicated coverage.
- **Requires the UI gate:** Yes, for the Matching center (S6) and Product preview/diff (S7) screens (Group 10) — though, per the Task 001 "core-only, zero-UI" precedent, the underlying binding/import backend logic is not necessarily gated on the UI implementation gate itself (Open — not decided in the repo, see Foundation dependency (b) above).
- **Requires the API-client gate:** Yes (Task 003) — both reads (product/variant queries) and controlled writes (`productSet`/bulk-variant mutations).
- **Requires domain model creation:** Yes, when authorized — product-template binding and product-variant binding models (exact names open, MBQ-55).

### 2. Customer import / matching

- **Why this position:** Customer binding is owned **directly** by `shopify_connector_sale` (not routed through `product`, since customers have no product-domain counterpart — Part B §B.8). Customer resolution is one of the two prerequisite legs (alongside product binding) that order finalization depends on — though per the accepted design "a failed customer import is isolated and reason-coded; the linked order still reconciles ... one bad customer record does not block order import" (Part B §C.6, quoting `phase1-domain-model-brief.md` Domain 4). It is sequenced here, ahead of Order import, because order finalization needs a customer-resolution outcome (success, fallback, or held-pending-review) even though a bad customer match does not block the rest of order import.
- **Dependencies:** `shopify_connector_sale` module (there is **no** separate `shopify_connector_customer` module in the accepted Phase 1 design — see "Domain boundaries" below); the core binding contract; email as the **sole** automatic match key (MBQ-31, "Accepted at blueprint level by DEC-014"); the single flagged fallback partner concept (MBQ-29).
- **Risks:** the protected-customer-data / no-PII posture — order import must not fail, nor invent PII, when Shopify genuinely withholds all customer fields (Part B §B.6); ambiguous-match routing to manual review; **address handling** and **company-vs-person (`res.partner.is_company`) classification** are both explicitly **"Open — not yet decided in the repo"** per the product/customer/sale research notes — neither DEC-014 nor Part B addresses either topic, and this document does not invent an answer.
- **Open MBQs:** MBQ-02/55 (exact partner field mapping / binding model name, open). MBQ-29 (default-customer fallback granularity) has **conflicting snapshots in the research notes**: the product/customer/sale notes describe it as "Partially resolved by DEC-014 ... what remains open: whether one shared fallback partner per store is sufficient, or whether per-order anonymous identity is required"; the later UI/UX notes state "per-order anonymous identity is explicitly non-MVP; only its exact naming is open (MBQ-29, 'Resolved via AR-020')." Both are reported here without reconciliation — a future task spec for this area should confirm the current register state directly rather than rely on either snapshot.
- **User value:** lets order import attribute a Shopify order to the correct Odoo customer record without duplicate creation, PII invention, or a silent, ungoverned default.
- **Testing complexity:** Medium — email-only auto-match correctness, ambiguous-match manual review, fallback-partner flagging/audibility on the order, and enforcement of "no customer export in Phase 1" (Part B §B.4).
- **Requires the UI gate:** Yes, for the Customer mapping screen (S8, Group 11) — Reviewer ambiguity-resolution flow.
- **Requires the API-client gate:** Yes (Task 003) — reads only; Phase 1 customer import is Shopify → Odoo only, never pushed back (Part B §B.2).
- **Requires domain model creation:** Yes, when authorized — a customer binding model owned by `sale` (exact name open, MBQ-55).

### 3. Order import

- **Why this position:** Cross-domain sequencing in Part B §D fixes this order structurally: "(1) Product binding must be available before order-line creation ...; (2) Customer binding/import must occur before order finalization ...; (3) The total-check guard ... is evaluated before the order is marked complete." Order import is therefore the first area that can only be attempted once both Area 1 and Area 2 exist.
- **Dependencies:** `shopify_connector_sale` (order binding — the sole idempotency anchor for order creation, Part B §C.1); product binding (Area 1) and customer binding (Area 2); the mandatory, permanent total-check guard (DEC-007 §6); the DEC-020 same-currency-only import posture (MBQ-64).
- **Risks:** the whole-order-hold rule for an unmatched product line (conservative by design; MBQ-57 logs a possible future revisit, not yet triggered); `financial total mismatch` handling must never be silent or auto-retried; `ORDERS_UPDATED` handling must remain evidence-refresh-only and must **never** silently update existing sale-order lines/prices/taxes/shipping/discounts/invoices/payments/refunds/fulfillment state (Part B §C.12, the Fable "B2" correction); divergent-currency orders (`presentmentCurrencyCode != currencyCode`) must be blocked from automatic sale-order creation "under any circumstance," independent of the numeric total-check guard's outcome (DEC-020, the "REVISE" correction).
- **Open MBQs:** MBQ-02/55 (order binding model/field names, open). MBQ-56 (exact total-check tolerance/comparison mechanism and exact Shopify total field — open; the open-questions register states it "blocks the order-import task"). MBQ-27 (mechanism for representing Shopify-computed tax on a sale order without Odoo's tax engine recomputing it — "not resolved, explicitly scoped ... requires a dedicated ADR + ChatGPT decision," per official verification finding no documented supported Odoo 19 mechanism). MBQ-58 (order-identity stability nuances beyond general GID non-permanence — accepted-open risk, not blocking). MBQ-30 (gateway → Odoo journal mapping schema, partially resolved). The DEC-020 residual: exact error-class/sub-reason mapping for a blocked divergent-currency order remains open, explicitly declined by DEC-020 itself pending a "named, deliberate" routing decision. MBQ-28 (Domain 9 draft-artifact guard — accepted-open risk, contingent, not triggered as of the cited research).
- **User value:** the core commerce event connecting Shopify sales to Odoo; the most operationally visible domain to a merchant.
- **Testing complexity:** High — total-check guard math across multiple evidence components (lines, tax, shipping, discount); same-currency-only enforcement; the three-path customer-resolution rule (no-PII fallback / ordinary import / ambiguous-hold); whole-order-hold retry loop; strict non-mutation of already-imported order lines on `ORDERS_UPDATED`.
- **Requires the UI gate:** Partially. MBQ-26 is already accepted (DEC-014 point C) as **no dedicated order-import screen** — order-import operator work instead extends the existing Error Center via two accepted additions (inline financial-evidence breakdown; direct link from `mapping missing` entries into the matching flow). So this area needs the UI gate only for those two Error Center extensions (Group 12), not a new screen.
- **Requires the API-client gate:** Yes (Task 003) — reads (order queries; webhook-triggered follow-up reads).
- **Requires domain model creation:** Yes, when authorized — an order binding model (exact name open, MBQ-55); no separate customer model beyond Area 2.

### 4. Inventory sync

- **Why this position:** Inventory depends only on `core` + `product`, and is an explicit **sibling** of `sale`, never depended on by `fulfillment` — "Inventory push and fulfillment creation are independent, siblings ... The only shared prerequisite between the two domains is the product's product-variant binding" (Part C, module-ownership section). It must follow Area 1 (product binding) but does not need to wait for Area 2 or Area 3 to complete; it is sequenced fourth here mainly because of its higher operational risk profile (live storefront stock), not a hard technical dependency on order import.
- **Dependencies:** `shopify_connector_inventory` (depends on `core` + `product` only); an explicit, non-inferred Odoo-location ↔ Shopify-Location mapping (owned solely by inventory, DEC-010); the mandatory first-push safety guardrails (mapped location + preview + operator confirmation + recorded source-of-truth decision + skip/manual-match ability); the standing Odoo-is-source-of-truth posture (DEC-010), with a one-time, reviewed Shopify baseline-import exception only.
- **Risks:** RA-020 (no autonomous bidirectional conflict resolution — a rejected approach, unweakened, must not be reintroduced); RA-018 (`committed` never a write target under any circumstance); RA-019 (per-location identity, never SKU-alone, to prevent double-decrementing a multi-location SKU); the Fable "C1" finding that `product.product.free_qty` and `stock.quant.available_quantity` are **not equivalent** and diverge whenever expired unreserved stock exists — described as "substantive, not cosmetic," and explicitly not decided by DEC-015.
- **Open MBQs — timeline note:** the inventory/fulfillment research notes (dated to DEC-015, 2026-07-03) describe MBQ-33 (first-push guard granularity) and MBQ-34 (ongoing apply-mode) as open **"[Recommendation]"** items only. The later mbq-cross-cutting research notes state both were subsequently **"Decided — DEC-018"** (MBQ-33: per mapped-location-pair granularity; MBQ-34: review-then-apply as the Phase 1 default). Both snapshots are reported here; the later DEC-018 status should be treated as the more current recorded decision, but a future task spec should confirm directly against the live register rather than rely on this document. Similarly: MBQ-35 (`available` vs. `on_hand`) is "carried forward, unchanged, open" in the earlier notes, but "resolved by conservative exclusion (AR-020)" — `on_hand` not exposed as a Phase 1 UI choice at all — per the later UI/UX notes. MBQ-32's core finding (the `free_qty`/`available_quantity` non-equivalence) is **not** resolved in either snapshot; only its exact aggregation mechanism residual is cited as later "closed via AR-020 as the conservative default" per the UI/UX notes, itself not independently verified in the two source files read for the inventory/fulfillment note-set. MBQ-38 (first-push confirmation-record schema) remains an open residual in every snapshot reviewed. MBQ-63 (inventory webhook payload/subscription mechanics) is reported in the mbq-cross-cutting notes as "decided by conservative exclusion: webhook-driven inventory import is not implemented in Phase 1."
- **User value:** keeps Shopify-facing stock aligned with Odoo's operational reality. Note: the research notes explicitly state that neither "negative stock" nor "oversell" appears as a named, discussed risk/edge case in the inventory/fulfillment source documents — the closest analog is the compare-and-set (`inventorySetQuantities`) preference for reducing stale-read race risk. Any future task spec should log an oversell-prevention posture as "Open — not yet decided in the repo" rather than assume one.
- **Testing complexity:** High — location-mapping ambiguity and no-inference enforcement, first-push preview/confirmation flow, compare-and-set concurrency handling, `committed`-never enforcement, multi-location double-decrement prevention.
- **Requires the UI gate:** Yes — Location mapping (S10), first-push guard (S11), and quantity/source-of-truth settings + ongoing apply queue (S12) are all dedicated screens (Group 13, risk rated "**High** — live storefront stock").
- **Requires the API-client gate:** Yes (Task 003) — reads (one-time baseline import) and writes (`inventorySetQuantities`/`inventoryAdjustQuantities`).
- **Requires domain model creation:** Yes, when authorized — the inventory-level binding keyed `(store, inventory_item_id, location_id)`, plus the location-mapping model (exact names open, MBQ-55-adjacent).

### 5. Fulfillment/tracking update

- **Why this position:** Fulfillment resolves order bindings through `sale` and product/variant bindings through `product`, and is explicitly stated to **never** depend on `inventory`: "Fulfillment never depends on inventory, structurally ... `fulfillment` must not read `inventory`'s Odoo-location ↔ Shopify-Location mapping table" (Part C, module-ownership section; DEC-008/010/011). Its trigger (a validated `stock.picking`) requires both an order binding (Area 3) and a product-variant binding (Area 1) to resolve stock-move lines to Shopify order line items — so it structurally needs Areas 1 and 3, but explicitly not Area 4.
- **Dependencies:** `shopify_connector_fulfillment` (depends on `core` + `sale` only, plus Odoo's own `stock`/`delivery`-family apps directly); the FulfillmentOrder-exclusive mutation posture (`fulfillmentCreate`/`fulfillmentTrackingInfoUpdate`; legacy Order/Fulfillment endpoints never used — RA-022); single-fulfillment-location Phase 1 scope; the `stock_delivery` (or `delivery`) module dependency for tracking fields (MBQ-60, Decided — DEC-018: required; absence is a named readiness/health blocker, never silently degraded).
- **Risks:** RA-023 (an unmatched picking is never fulfilled by guess — blocks for manual review, unweakened); fulfillment mutations are **not** on Shopify's `@idempotent` list (unlike inventory's `inventorySetQuantities`), so an ambiguous-outcome failure requires a safe verification read before retry, never a blind retry (RA-014), plus a combined operation-level idempotency key **and** serialization guard (both required together, neither sufficient alone); the customer-notification default must stay off unless explicitly enabled, and the decision must be persisted at enqueue time, never re-read at retry (RA-009).
- **Open MBQs:** MBQ-40 (backorder-linkage field confirmed at fact-verification level; the delivery-wizard UX/copy nuance is an open residual, not independently re-verified). MBQ-42/MBQ-43 (fulfillment location-confirmation mechanism and Shopify-Location cache-refresh cadence — accepted at blueprint level, with open implementation-level residuals). MBQ-61 (FulfillmentOrder lifecycle events beyond simple creation — holds/cancellations/merges/splits/moves/reschedules — per the mbq-cross-cutting notes, "decided by conservative exclusion: Phase 1 does not subscribe to the `FULFILLMENT_ORDERS_*` lifecycle family"). MBQ-41 (notification-UI granularity — Decided, DEC-018: global/per-store default sufficient for Phase 1; per-order override deferred). MBQ-21/MBQ-20 (serialization-guard exact mechanism and idempotency-key schema, shared across domains, open at the implementation-mechanics level).
- **User value:** closes the operational loop by giving merchants/customers accurate shipment/tracking visibility tied to real Odoo warehouse fulfillment events.
- **Testing complexity:** High — non-idempotent-mutation handling via verification-read-before-retry, backorder/partial-fulfillment sequencing (each picking in a chain fulfilled independently, never merged), notification-suppression-by-default correctness, FulfillmentOrder-location mismatch handling, and `stock_delivery` absence handling.
- **Requires the UI gate:** Yes — rendered through the shared Sync Center/Error Center plus a small notification-settings sub-surface (Group 14, risk rated "**High** — customer-facing side effects"); no parallel fulfillment monitor (RA-013).
- **Requires the API-client gate:** Yes (Task 003) — writes (`fulfillmentCreate`, `fulfillmentTrackingInfoUpdate`) plus verification reads.
- **Requires domain model creation:** Yes, when authorized — a FulfillmentOrder/Fulfillment binding model keyed `(store, Shopify FulfillmentOrder GID)` (exact name open, MBQ-55-adjacent).

### 6. Manual sync / scheduled sync hooks

- **Why this position:** each of Areas 1–5 already carries its own layered-sync posture (webhook / manual / scheduled / reconciliation / Odoo-event, "never webhook-only" — DEC-005) inside its own blueprint section. This area is placed sixth not because the shared sync-trigger substrate can only be *built* after the five domains exist — the underlying mechanism (the `job` model's `job_source`/`trigger_origin` vocabulary) is core-owned and already exists in accepted form — but because verifying and consolidating the cross-domain manual/scheduled/reconciliation behavior consistently across all five domains is naturally a step that follows once each domain's own job-producing logic is defined.
- **Dependencies:** the DEC-005 layered-sync pattern applied per domain; the accepted seven-value `job_source` vocabulary (`webhook`, `manual_sync`, `scheduled_sync`, `reconciliation`, `setup_readiness_check`, `export_preview_dry_run`, and `odoo_event` — the last one added by DEC-019 specifically for Odoo-side event triggers such as an inventory push from a stock change or a fulfillment creation from a validated picking); MBQ-17 (reconciliation cadence).
- **Risks:** re-introducing the Fable "C2" error of treating "event-driven enqueue" as its own new `job_source` value rather than using the already-accepted `odoo_event` value with a `trigger_origin` sub-classification (corrected by DEC-019); treating webhooks as a sufficient sole mechanism — Shopify's own cited guidance states "your app shouldn't rely on receiving data from Shopify webhooks ... use reconciliation jobs," restated for product webhooks specifically in DEC-020/MBQ-65.
- **Open MBQs:** MBQ-17 (per-store, per-domain reconciliation posture is Decided — DEC-018; the exact cadence/batch-size residual remains open per the task map's Group 2 prerequisite listing). MBQ-62 (the `odoo_event` job-source **value and semantics** are Decided — DEC-019; the mbq-cross-cutting notes report the residual field/model mechanics as "resolved by ChatGPT via PR #85 / AR-019 / core-naming-schema-planning.md," a later document not independently verified in this research pass — flagged, not asserted, here). MBQ-16 (retry/backoff constants — "resolved as adjustable defaults," not final production values). MBQ-50 (OCA `queue_job` optional-accelerator adoption — accepted-open risk, gated on DEC-005's own revisit triggers, not a Phase 1 default).
- **User value:** gives the operator confidence that data reconciles even when a webhook is missed, delayed, or delivered out of order — the correctness backstop behind every domain area above.
- **Testing complexity:** Medium-high — must be exercised **per domain** (each domain's own reconciliation pass re-verifies its own previously-synced records — orders re-verify totals, inventory re-verifies quantities, fulfillment re-verifies status) rather than as one generic mechanism, per the accepted "never one global cross-domain job" posture.
- **Requires the UI gate:** Yes, for the manual "sync now" quick-action affordance and any scheduled-cadence settings surface, which render through the Dashboard/Sync Center (Groups 2, 8) — core/shared surfaces requiring the UI gate but no domain-specific "domain gate" of their own.
- **Requires the API-client gate:** Indirectly yes — manual/scheduled/reconciliation jobs execute through the same domain job handlers and single API client described in Areas 1–5; this area adds no new API-call authority of its own.
- **Requires domain model creation:** No new binding models; extends the existing core job model's `job_source`/`trigger_origin` vocabulary (already accepted, DEC-019) and reuses each domain's own binding models from Areas 1–5.

### 7. Dashboard/sync/error center operational views

- **Why this position:** the Dashboard (S3), Sync Center (S4), and Error Center (S5) are accepted as **shared, cross-domain surfaces** that "domain modules contribute, never fork" (RA-013) — they consolidate the job/log/error data produced by Areas 1–6, so they have meaningful content only once at least some domain job-producing logic exists, even though structurally they are core-owned screens (Groups 2, 8, 9) that do not themselves require a domain-specific "domain gate."
- **Dependencies:** the core job/job.log substrate (data model already exists per the Task 001 precedent — model-only, no views); the nine accepted, fixed Dashboard cards (connection health; last successful sync per domain; failed jobs by severity; manual-review count by sub-reason; retry-waiting count; first-push-pending count; inventory exceptions; fulfillment exceptions; duplicate/matching exceptions); the Error Center's accepted nine-element entry contract and the fixed vocabulary of six manual-review sub-reasons; the two accepted order-import Error Center extensions.
- **Risks:** adding an unaccepted tenth Dashboard card — "any additional card requires a new accepted decision" (the deferred "Daily Queue Activity" chart idea is explicitly logged as a deferred candidate, not adopted); forking a per-domain dashboard/error queue (RA-013, forbidden); rendering an internal token or raw stack trace as a primary label (RA-016, forbidden); collapsing Sync Center and Error Center into one surface (explicitly rejected — "monitoring ('what ran') vs. recovery ('what needs a decision') are different mental modes").
- **Open MBQs:** MBQ-53 (the full screen-level UI/UX design blueprint — the register states it "stays OPEN/partial, not fully resolved" even after DEC-016's screen-design-blueprint-level acceptance, and "Blocks implementation: Yes, for implementation of any operator-facing screen/view/UI flow"). MBQ-03 (exact XML/view/menu/action IDs — routed/descoped but not fixed). MBQ-22 (exact copy — routed/descoped but not fixed). MBQ-51 (GraphQL cost/throttle pacing parameters feeding the Dashboard's API-health signal — "remains open, still Implementation planning"). The primary MVP persona (RB-13) — open, affects emphasis not structure.
- **User value:** the single day-to-day operator-facing surface; without it, none of Areas 1–6 are auditable or operable by a human — "the most stressful screen in any connector is this product's calmest," per the accepted design intent for the Error Center specifically.
- **Testing complexity:** Medium — primarily a rendering/aggregation layer over an already-designed job/log data shape; complexity concentrates in role-gating, fixed-vocabulary correctness (7 job sources, 10 job states, 16 error classes with no 17th, 6 manual-review sub-reasons, 4 retry UI cases), and the two order-import-specific Error Center extensions.
- **Requires the UI gate:** Yes — this area **is** the core/shared portion of the UI implementation gate's work (Groups 1–2, 8–9); it requires the UI gate to be opened but no business "domain gate" (product/sale/inventory/fulfillment) of its own.
- **Requires the API-client gate:** No new API-call surface of its own — it only displays data already captured by domain jobs/logs from Areas 1–6.
- **Requires domain model creation:** No new binding models; consumes the core `job`/`job.log` models and whatever domain binding models from Areas 1–5 already exist by the time it ships meaningful per-domain content.

### 8. MVP release hardening

- **Why this position:** a cross-cutting closure pass over Areas 1–7 — verifying that the whole MVP scope (product/variants, customers, orders, inventory, fulfillment/tracking, manual/scheduled sync, operational logs/retry — see "MVP vs later" below) holds together end-to-end before any release-readiness claim is made. By definition it cannot precede the areas it hardens.
- **Dependencies:** Areas 1–7 merged and reviewed; the phase-exit criteria referenced in CLAUDE.md §12 (`docs/05-qa/quality-feedback-loop.md` §10, itself currently `[Recommendation — becomes binding when merged by ChatGPT]`); the accepted implementation-phase gates in `docs/05-qa/pr-review-checklist.md` Section C (idempotency/duplicate prevention; error handling; retry/recovery; rate-limit awareness; security/permissions; performance; tests including prior defects and edge cases; rollback notes; definition of done; technical-debt logging).
- **Risks:** scope creep back into deferred/Later items (payouts, advanced refunds, Shopify Markets, multi-store/multi-company complexity, metafields, subscriptions, gift cards, POS, B2B, advanced analytics, App Store packaging) — must be checked against DEC-003's already-finalized MVP baseline, never re-derived from scratch; declaring readiness while a correctness-relevant residual (e.g., MBQ-27 tax representation, MBQ-56 total-check tolerance) remains genuinely unresolved rather than merely cosmetic.
- **Open MBQs:** whichever of Areas 1–5's open MBQs remain unresolved at hardening time — this document does not resolve any of them. Explicitly cross-cutting items to re-check: MBQ-12 (Shopify GID permanence/non-reuse — "accepted-open risk," may remain permanently unresolved without blocking anything, since the defensive stale/review design does not depend on the answer) and MBQ-50 (OCA `queue_job` adoption — accepted-open risk).
- **User value:** the difference between "the pieces work individually" and "a merchant can trust the connector as a coherent product" — end-to-end scenario coverage, rollback readiness, and a defensible definition of done.
- **Testing complexity:** Highest of the eight areas — full end-to-end scenarios (a single Shopify order touching product, customer, inventory, and fulfillment together), regression testing against every prior defect/rejected approach in `docs/05-qa/rejected-approaches-log.md`, and behavior under realistic catalog/order volume and Shopify rate limits.
- **Requires the UI gate:** Yes, insofar as UI is in MVP scope at all (Groups 1–14 collectively) — hardening verifies the whole shipped surface, core and domain alike.
- **Requires the API-client gate:** Yes — verifies real end-to-end Shopify interaction across every domain's read/write paths.
- **Requires domain model creation:** No new models of its own — a verification/hardening pass over models created in Areas 1–5.

## Domain boundaries

The following module boundaries are a **planning-only proposal**. Naming a module here is not code authorization — no module directory, manifest, model, or file may be created on the strength of this document.

- **`shopify_connector_product`** — owns product/variant import, controlled export/update, and product/variant binding responsibility (Part B §A.8; DEC-008-derived). Depends only on `core`.
- **`shopify_connector_customer`** — **not part of the accepted Phase 1 module set.** Per DEC-008 (restated in Part B §B.8), customer import/matching is **folded into `shopify_connector_sale`** for Phase 1 — "there is no separate `shopify_connector_customer` module." A future, independent `shopify_connector_customer` module is named in the research notes only as a **possible future promotion**, explicitly classified "Weakened/deferred, not rejected" with its own stated revisit condition ("legitimate later split once demonstrated"), per `ar004-module-boundary-decision-brief.md`. This document does not propose promoting it now, and per CLAUDE.md §10 any future proposal to split it out would need to be routed through architecture review, not silently re-introduced.
- **`shopify_connector_sale`** — owns **both** the order domain (import, financial-evidence capture, the total-check guard) **and** the customer domain (import/matching, folded in per DEC-008). Depends on `core` + `product`; is a sibling of `inventory`.
- **`shopify_connector_inventory`** — owns inventory quantity sync, the Odoo-location ↔ Shopify-Location mapping (sole owner), and the first-push guard. Depends on `core` + `product` only; sibling of `sale`; never depended on by `fulfillment`.
- **`shopify_connector_fulfillment`** — owns fulfilment/tracking write-back and the customer-notification guard. Depends on `core` + `sale` only (plus Odoo's own `stock`/`delivery`-family apps directly); never depends on `inventory`.
- **Later accounting/refund/payout/multi-store modules** — not designed, named, or bounded by any accepted decision read for this pass. Order edits, cancellations, refunds, and returns remain fully deferred (DEC-003, unchanged); payout reconciliation, advanced refunds, and multi-store/multi-company complexity are Later/out-of-scope items (see "MVP vs later" below). Any future module boundary for these areas would require its own architecture-review pass — none is proposed here.

On naming convention: the module-name pattern above (`shopify_connector_<domain>`) and the `shopify.connector.<entity>` model-name prefix are already an **accepted planning convention**, per `core-naming-schema-planning.md` (Accepted by ChatGPT, 2026-07-05): *"Later domain modules (`shopify_connector_product`, `_sale`, `_inventory`, `_fulfillment`) are expected to continue this convention for their own concrete binding models (MBQ-55, out of scope here) so the naming scheme stays consistent connector-wide without a later rename."* What is **not** yet decided is the exact binding-model name and field schema **inside** each of these modules — that is MBQ-55, explicitly open, and this document does not resolve it. Where this document proposes specific binding-model roles (e.g., "product-template binding," "product-variant binding," "order binding," "inventory-level binding," "FulfillmentOrder/Fulfillment binding") it is describing accepted **roles/shapes** from DEC-013/DEC-014/DEC-015, not proposing exact technical names — those remain a recommendation pending the dedicated MBQ-55 naming/schema pass.

## Cross-domain shared concerns

### Binding model pattern (reusing the accepted `binding.mixin`)

Every domain binding described above is expected to extend the existing accepted abstract `shopify.connector.binding.mixin` rather than invent a new binding shape or a polymorphic table. The mixin supplies `store_id`, `shopify_gid`, `status` (`active`/`stale`/`manually_overridden`/`review`), `match_key`, `matched_by_uid`/`matched_at`, and override-tracking fields; it deliberately does **not** include a generic `res_model`/`res_id` pair — each concrete domain binding model is expected to add its own specific link to the Odoo business object it binds, per DEC-013's "one concrete binding model per synchronized root entity" rule. This yields exactly the roles already named in the research: product-template binding, product-variant binding, customer binding, order binding, inventory-level binding (`store, inventory_item_id, location_id`), and FulfillmentOrder/Fulfillment binding (`store, Shopify FulfillmentOrder GID`) — "No new binding shape, no polymorphic table, and no per-domain audit variant is introduced."

### Duplicate prevention

Two paths are already accepted and must be preserved by every domain: (1) an **interactive/batch path** — any interactive or batch create/bind action always shows a blocking preview before the operator confirms; and (2) an **automated path** (webhook/scheduled/reconciliation-triggered) — a pre-create duplicate check runs before creating/binding, gated by the accepted two-tier gate (eligibility conditions, then match-quality conditions) from MBQ-59, "accepted at blueprint-policy level" with exact eligibility-check/match-confidence thresholds left open for implementation planning. Retrospective sync-center/dashboard visibility alone does **not** satisfy the no-blind-create requirement — that was an earlier draft error, explicitly corrected.

### Idempotency

The order binding is the sole idempotency anchor for order creation; equivalent per-domain bindings apply the same pattern for product, customer, and inventory. GID permanence is not asserted by Shopify for any object (MBQ-12, open, non-blocking), so stale/recreated-binding handling applies uniformly. Fulfillment mutations are **not** on Shopify's `@idempotent` list, so fulfillment additionally requires the combined operation-level idempotency key **and** verification-read-before-retry pattern — both required together, neither sufficient alone.

### Job queue usage

All business sync/write work is expected to be represented as a `shopify.connector.job` record, using the accepted `job_type` extension seam (domain modules register via `selection_add`), the fixed `job_source` vocabulary (including the DEC-019 `odoo_event` value with its `trigger_origin` sub-classification), and the fixed 16-class `error_class` registry (domain modules do not add new top-level error classes without a DEC-level change).

### Error / manual-review routing

Every domain reuses the same accepted registry rather than inventing per-domain manual-review mechanisms: the fixed six manual-review sub-reasons (ambiguous match; binding conflict; duplicate risk; destructive-write guard blocked; inventory location missing; fulfillment notification confirmation missing), and the distinction between `blocked_manual_review` (confirmation required) and `failed_retryable` (e.g., `mapping missing` for an unmatched product line — "manual fix then retry," explicitly not routed to `blocked_manual_review`).

### Retry behavior

Retry is class-conditional, not blanket: reads and `@idempotent`-eligible operations auto-retry on transient/network errors; ambiguous-outcome failures require a safe verification read before any retry, never a blind retry (RA-014); `financial total mismatch` is conservative, never silent, never auto-retried; terminal states carry no retry control and no "force" bypass exists anywhere.

### Logs / audit

Every state transition is expected to write a corresponding append-only `shopify.connector.job.log` row (`ondelete='restrict'`, never cascade-deleted), carrying a human-readable `message`, an expandable `technical_detail`, and a `payload_snapshot` for evidence. Binding records carry their own audit fields (matched-by, matched-at, source strategy, match key, override history). No domain invents a parallel logging mechanism.

### Mapping screens

Product/variant matching, customer matching, and inventory location mapping each get their own dedicated mapping/matching-center screen (S6, S8, S10) once the UI gate opens, each following the same fixed match-key-priority pattern (existing binding first, then a domain-specific automatic key, then manual review) and the same three-visual-state pattern (unmatched / ambiguous / duplicate risk) rather than three independently-designed UIs.

### Premium UX requirements

Every future domain screen is expected to satisfy the same accepted, cross-cutting bar: the twelve UX principles (setup simplicity, safe defaults, no silent sync, operator confidence via stage→inspect→process→verify→log, explainable errors, retry/recovery first, Odoo-native patterns, human-friendly language, progressive disclosure, calm error handling, one clear next action per state, no jargon on the action path); the "Premium Simplicity Standard" ("premium means clarity, confidence, polish, guidance, and recovery," not more screens/colors/charts/complexity); and the universal must-not-dos (never modify `adams_base` or non-connector code; never fork a per-domain dashboard/queue; never render an internal token or raw stack trace as a primary label; never add a guard bypass; never claim encryption in credential copy; never widen MVP scope).

### Permissions

All domains reuse the same four existing access groups (`group_shopify_connector_auditor`, `_operator`, `_reviewer`, `_admin`) on one shared, role-gated surface — "domain modules contribute, never fork" — rather than minting new domain-specific groups. Exact per-domain access rows remain implementation-planning detail (MBQ-44 residual, open).

### No direct Shopify writes outside the approved API client

This is a structural rule every domain must respect: `shopify_connector_core` is "the single place any connector module talks to Shopify." Domain modules never construct requests, read credentials, or parse raw Shopify errors themselves — they call the client only from job handlers registered through the accepted job-type seam. Duplicating transport/queue/log/binding abstractions per domain is a rejected approach (RA-013).

### No direct sync outside the job/queue substrate

Equally structural: no business sync/write job is enqueueable-to-run for a store whose setup is incomplete, enforced in the queue substrate itself at both enqueue time and execution time (defense in depth) — never only hidden in the UI. `setup_readiness_check` and `export_preview_dry_run` jobs are the sole accepted exceptions, and they are themselves structurally read-only/preview-only, never business writes.

## MVP vs later

**MVP includes:**
- Products and variants (import, controlled export/update, variant-level binding).
- Customers (import/matching, folded into the sale domain for Phase 1; no export).
- Orders (import, financial-evidence capture, total-check guard, same-currency-only automatic import).
- Inventory (Odoo-as-source-of-truth quantity sync, explicit location mapping, first-push guard).
- Fulfillment/tracking (FulfillmentOrder-based creation and tracking updates, single-fulfillment-location scope).
- Manual sync / scheduled sync (layered with webhook and reconciliation, never webhook-only).
- Operational logs / retry (shared job/log substrate, Dashboard, Sync Center, Error Center, class-conditional retry).

**Later / out of scope for MVP:**
- Payouts.
- Advanced refunds.
- Shopify Markets.
- Multi-store / multi-company complexity.
- Metafields.
- Subscriptions.
- Gift cards.
- POS.
- B2B.
- Advanced analytics.
- App Store packaging.

Also explicitly deferred, unchanged from DEC-003 and restated across the research notes (relevant context, not new scope items): order edits/cancellations/refunds/returns from Shopify (evidence-refresh only, never re-applied to the Odoo sale order); autonomous bidirectional inventory conflict resolution; per-order notification override for fulfillment (global/per-store default only in MVP); FulfillmentOrder lifecycle events beyond simple creation (holds/cancellations/merges/splits); true multi-package ("Put-in-Pack") fulfillment splitting and multi-location fulfillment automation; presentment-currency-denominated Odoo orders (divergent-currency orders are blocked from automatic import, not specially supported); merchant-facing domain-module uninstall (disable-not-uninstall only).
